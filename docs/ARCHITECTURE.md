# 架构与设计取舍

## 一句话

**归一化（把变形折叠回规范形）→ 判决（字符级模型）→ 分级处置（按置信度分流）→ 可追溯（证据链 + 定位图）**。

四层里任何一层单独拿出来都不新鲜，组合起来的价值在于：每一层都有对应的评测切面，
出问题能定位到具体是哪一层失效。

```
                       ┌──────────────────────────────────────────┐
  原始内容 ────────────▶│  L1 归一化层  raven/normalize.py          │
  （文本 / 图片）        │  NFKC→零宽→emoji→小写→拼音缩写→         │
                       │  折叠分隔符→谐音→繁简→再折叠→重复字符    │
                       └───────────────┬──────────────────────────┘
                                       │ 规范形 + 逐步 trace
                       ┌───────────────▼──────────────────────────┐
                       │  L2 判决层                               │
                       │  文本：字符 1~3gram 哈希(8192) + 规则证据  │
                       │        特征 → 逻辑回归 → p                │
                       │  图片：ELA / 噪声残差 / ghost 块级特征    │
                       │        → 逻辑回归 → p + 热力图            │
                       └───────────────┬──────────────────────────┘
                                       │ p
                       ┌───────────────▼──────────────────────────┐
                       │  L3 处置层  pipeline.decide()             │
                       │  p≥0.82 拦截 │ ≥0.68 人工复核 │ ≥0.40 观察 │
                       └───────────────┬──────────────────────────┘
                                       │
                       ┌───────────────▼──────────────────────────┐
                       │  L4 可追溯层                              │
                       │  归一化 trace / 还原命中的词 / 类目分     │
                       │  / 否定语境信号 / 块级热力图              │
                       └──────────────────────────────────────────┘
                                       │
                    同一份代码 ─────────┴─────────▶ 评测 / CLI / demo / 报告
```

## 关键不变式

这三条是这个项目里最"工程"的部分，也是我在复现论文和做检测平台时吃过亏的地方：

1. **评测与线上跑同一份代码。**
   `eval/run_eval.py` 不重写打分层，而是 import `TextEngine`。否则"评测 0.93、上线一团乱"是必然。

2. **权重可以被导出、被复现。**
   `artifacts/models/engine.json` 里是裸权重 + 词表 + 阈值。浏览器端 `demo/raven-lite.js`
   用它重新实现了一遍推理，并用 225 条样本与后端对拍（当前最大概率差 5e-5）。
   能导出、能对拍，才说明这套逻辑没有藏在黑盒里。

3. **每个数字都能一条命令重跑。**
   `python run_all.py`，57 秒，全程 CPU、无网络。

## 为什么是字符 n-gram，不是分词 + BERT

| 方案 | 为什么没用 |
|---|---|
| jieba 分词 + TF-IDF | 黑产文本本来就在破坏分词（插符号、拆字），分词器的错误会直接传导到特征 |
| 预训练模型（BERT 类） | 660 条训练样本微调大模型必然过拟合；且要求装 torch，评审方 clone 下来跑不动 |
| 规则 + 词表 | 就是消融表里的 ①，逐字符分隔集 F1 = 0.000 |
| **字符 1~3 gram + 线性模型** | 抗插入/抗删改、训练 5 秒、权重可导出到浏览器，且在这个数据量级上更稳 |

代价也要说清楚：字符 n-gram 不懂否定、不懂语序，所以"举报卖外挂的人"和"卖外挂"在它眼里很像。
这个缺陷在误报分析里被完整暴露出来了（18 条误报，几乎全是这类），并在路线图里给出了解法（LLM 复核灰区）。

## 图像侧为什么只是"粗筛"

复现 FUSED 之后我意识到一件事：深度取证模型给的是精度上限，但它的成本和不可解释性在生产里很贵。
所以这一层的定位是**前置过滤器**：毫秒级、纯 CPU、给出块级热力图，把可疑图挑出来再送深度模型。
它的指标（AUC 0.973，定位命中率 0.30）说明它够格当过滤器，不够格当终审——
这句话必须写在文档里，否则就是自欺。

## 文件职责

| 文件 | 职责 | 不该做什么 |
|---|---|---|
| `normalize.py` | 只做字符折叠，不做判断 | 不引入任何阈值或业务规则 |
| `text_model.py` | 特征、模型、规则打分 | 不做处置决策 |
| `image_forensics.py` | 特征提取 + 定位图 | 不读数据集、不训练 |
| `lexicon.py` | 所有词表与阈值的唯一来源 | 不写逻辑 |
| `pipeline.py` | 组装、训练、打包权重 | 不做评测指标计算 |
| `eval/run_eval.py` | 评测、消融、选阈值 | 不改引擎行为 |
| `raven/report.py` | 只读 metrics.json 渲染 | 不重新算指标 |

一个细节：`lexicon.py` 被生成器（正向变形）和归一化层（反向折叠）**共用**。
共用的好处是"我造的变形"和"我能还原的变形"在同一假设空间；
坏处是这构成了一个隐含的循环论证，所以评测里专门加了 `test_holdout`（归一化词表里没有的变体）来标定这个假设的上限。
