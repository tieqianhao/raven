# 模拟环境 · 60 分钟社区攻防演练

`eval/run_eval.py` 回答的是"模型准不准"：四套测试集打一遍，算 P/R/F1。

它回答不了上线之后的问题：**每分钟会拦几条、审核会不会堵、漏掉的单条能不能靠账号兜回来。**
这个目录就是补这一层——把三套变形测试集编排成一条 60 分钟时间轴，用同一个引擎跑一遍。

```bash
python sim/run_sim.py                  # 跑一遍，出指标 + 看板
python sim/run_sim.py --no-dashboard   # 只要指标
python sim/run_sim.py --review-capacity 6   # 换审核产能再看
```

产物：

| 文件 | 内容 |
|---|---|
| `artifacts/sim/dashboard.html` | 单文件看板，可播放重放，断网也能开 |
| `artifacts/sim/sim_metrics.json` | 全部模拟指标（含对账结果） |
| `artifacts/sim/events.jsonl` | 逐条事件（含归一化前后、概率、处置） |

---

## 场景怎么定的

| 阶段 | 时间窗 | 条数 | 内容 |
|---|---|---|---|
| 基线流量 | 0–60 min | 270 | 未变形的日常发帖，混着直白广告与举报语境 |
| 第一波 · 混合变形 | 6–28 min | 270 | 繁体 / 全角 / 零宽 / emoji 填充 / 重复字符叠用 |
| 第二波 · 逐字符分隔 | 30–46 min | 270 | 每字之间插空格或 emoji，关键词规则归零 |
| 第三波 · 未登录谐音 | 48–58 min | 270 | 训练集没出现过的写法（外桂 / 辅住 / 代煉） |

编排依据不是随手拍的时间：攻击者一轮打不通会换手法，所以三波串行；每波内部前密后疏
（开打集中刷屏，被限流后衰减）；基线全程均匀铺开——**误报只能在正常流量里量，塞进攻击样本里量不出来**。

账号沿用数据集自带的 `account` 字段。同一个 ID 会在不同波次出现，相当于"同一个人换着手法发"，
这也是账号级聚合有意义的前提。

---

## 判定和处置是两套阈值

这是本项目里一个真实存在、之前没被写下来的缝：

- **分类**用 `p ≥ 0.38`（`engine.json` 里的二分类阈值，与 `eval/run_eval.py` 同源）
- **处置**分档用 `0.82 / 0.68 / 0.40`（`lexicon.THRESHOLDS`）

中间 `0.38 ~ 0.40` 是个缝：模型说"这是违规"，处置层却说"放行"。
本次演练有 **7 条**落在这个缝里（5 条正常 + 2 条违规）。

两种改法，都得连带重采基线：

1. 把 `watch` 阈值从 0.40 降到 0.38，让分档覆盖二分类的判决边界；
2. 或者把二分类阈值提到 0.40，代价是召回略降。

没有直接改，是因为动阈值要同步 `tools/check_metrics.py` 基线、`README.md`、`docs/EVAL.md` 三处，
属于独立的一次改动。这里先把现象记下来。

## 本次运行的结果

分类口径 `p ≥ 0.38`，与 `metrics.json` 逐位同源：

| 波次 | 条数 | 违规 | 精确率 | 召回 | F1 | 评测 F1 | 差 |
|---|---|---|---|---|---|---|---|
| 基线流量 | 270 | 180 | 0.9206 | 0.9667 | 0.9431 | 0.9431 | 0 |
| 第一波 混合变形 | 270 | 180 | 0.9053 | 0.9556 | 0.9297 | 0.9297 | 0 |
| 第二波 逐字符分隔 | 270 | 180 | 0.9402 | 0.9611 | 0.9505 | 0.9505 | 0 |
| 第三波 未登录谐音 | 270 | 180 | 0.9763 | 0.9167 | 0.9456 | 0.9456 | 0 |

**差全是 0 不是巧合**：同一个 `TextEngine`、同一份 `engine.json`、同一批 `jsonl`。
`run_sim.py` 末尾会自动对账，有差就返回非零退出码。模拟环境不允许自己造数字。

处置分档（1080 条池化）：

| 档位 | 条数 | 其中违规 | 精确率 | 覆盖违规 |
|---|---|---|---|---|
| 拦截 `p≥0.82` | 598 | 598 | 1.000 | 83.1% |
| 限流 + 复核 `p≥0.68` | 58 | 49 | 0.845 | 6.8% |
| 观察 `p≥0.40` | 69 | 35 | 0.507 | 4.9% |
| 放行 | 355 | 38 | 0.107 | 5.3% |

审核队列（1 个工位、12 条/分钟、观察档抽检 10%）：进审 66 条，占 6.1%；
峰值积压 2 条，平均等待 0.01 分钟，工位利用率 9%。

---

## 三个值得拿出去讲的结论

**1. 瓶颈不在审核人力。**
66 条进审摊到 60 分钟是 1.1 条/分钟，单工位产能 12 条/分钟，利用率 9%。
所以"要不要加审核员"是个伪问题，真正该投的是召回和阈值——灰区少一条，人工就少一条。

**2. 账号兜底率 100%，但这个数没有区分度。**
36 条漏检全部来自发帖 ≥2 条的账号，聚合必然兜住。这套数据每个账号平均 6.6 条，
换成"一个账号只发一条"的真实分布，兜底率会直接归零。
所以它说明的是"账号重复发帖时聚合有效"，**不能当独立检测能力宣传**——面试被追问一句就会露。

**3. 阈值缝隙会吃掉一部分真实召回，而且不体现在 F1 里。**
7 条落在 0.38~0.40，模型判违规、处置放行。F1 按 0.38 算，看不见这 7 条；
只有把"判定"和"处置"分开摆，缝才露出来。这正是静态评测最容易漏掉的一类问题。

## 与评测的口径差异（别混用）

| 指标 | 本模拟 | EVAL | 为什么不同 |
|---|---|---|---|
| 分档表 | 1080 条池化 | `test_adv` 单集 151 条 | 分母不同 |
| 账号级 F1 | 0.9969 | 0.9512 | 池化后每账号 6.6 条 ≈ 多次投票 |
| 单条时延 | p50 ≈ 0.2 ms | 0.3~0.5 ms | EVAL 在训练后立刻采 120 条，含冷启动 |

时延这一行不要报精确值：同一份代码在不同负载下能在 0.18~0.46 ms 之间漂，
所以对外只说区间。评测自己测到的值以 `artifacts/results/metrics.json` 的 `text.latency_ms` 为准，
本仓库不在这里抄一份——抄了就会跟着过期。

还有一条最重要的：**本次演练的违规内容占 66.7%**（合成数据按 2:1 抽样），真实社区远低于此。
所以"拦截 598 条"这种绝对量不能当线上容量规划的依据，只能看比例和相对关系。

---

## 边界

- 数据是合成的，时间轴是我按"攻击者换手法"的假设排的，不是真实流量回放。
- 审核产能、抽检率是人为假设，换数值结论就变——所以它们写在看板页脚，和实测值分开列。
- 图像侧没有进模拟，只做了文本。
- 一个账号跨波次出现，会让账号级指标偏高；这是取舍，不是疏忽。
